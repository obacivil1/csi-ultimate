# الهيكل الخبير لأنظمة السكرابر الاحترافية — إطار مرجعي منهجي
### Scraper Systems Reference Architecture (SSRA) v2.0 — EXPERT EDITION

> **المراجعة:** بعد تحليل v1.0 وتقارير المشروع (SCRAPER_AUDIT + SCRAPER_ANALYSIS_2026-09-12)
> **الجمهور:** مهندس تطوير سينيور / استشاري — يُستخدم كـ **Standard + Playbook + Checklist** معاً
> **المرجعية العلمية:** Resilience Engineering (Hollnagel)، Site Reliability Engineering (Google/Wolter)، IEEE-830 (متطلبات)، SOLID/Domain-Driven Design (Evans)، OWASP، RFC-9110، أفضل ممارسات الويب (Web Sustainability Guidelines جزئياً)
> **طبيعة هذا الملف:** ليس وصفة جاهزة — بل **هيكل قرار (decision framework)** تُقرأ منه القرارات الصحيحة حسب حالة كل موقع وكل هدف.

## جدول المحتويات
```
0.  فلسفة الحوكمة والمبادئ غير القابلة للتفاوض
1.  تصنيف "العدو": نظاما الحماية + نظاما الموقع نفسه (بيئة مزدوجة)
2.  سلم التصعيد الذكي (Escalation Ladder) + قاعدة التوقف الكمية
3.  المعمارية الطبقية (12-Layer) مع العقود بين الطبقات
4.  الأنماط الهندسية الإلزامية (Resilience Patterns)
5.  طبقة البيانات الموحدة (Single Source of Truth)
6.  هرم اختبار السكرابر + ملفات ذهبية (Golden Fixtures)
7.  المراقبة والقياس: حزمة مقاييس إلزامية + لوحة قرار
8.  الحوكمة: ملكية + ADR + سياسة الإهلاك
9.  نموذج النضج L1–L5 مع معايير الخروج (Exit Criteria) كمية
10. دورة التطوير الديناميكي (SLAM Loop): اصنع–اثبت–تكيف–تعلّم
11. تعريف "الإنجاز" لكل مهمة (Definition of Done)
12. المصفوفة الأمنية والقانونية (Ethics & Compliance)
13. مصفوفة الفجوات المطبقة على CSI-Ultimate + خارطة طريق
14. مراجع علمية وعملية + معجم مصطلحات
```

## 0. فلسفة الحوكمة والمبادئ غير القابلة للتفاوض

PRIME DIRECTIVE: **نظام السكرابنج الناجح نظامٌ لا يُقاس بـ "كم زحفنا" بل بـ "كم فشلنا بأمان، وكم تعلمنا من الفشل".** الفشل هو الوحدة الأساسية للمعلومات — لا العيب.

| # | المبدأ | المعنى التشغيلي المجسَّد |
|---|---|---|
| 1 | **التحلّل اللطيف (Graceful Degradation)** | كل طلب له سلم قيم: API → RSS → HTTP-parse → Browser → Stealth → Extern → Proxy → Pause. التحلل خطوة، لا سقوط حر |
| 2 | **العزل الكامل (Bulkhead/Isolation)** | موقع واحد محظور = موقع واحد محظور. لا تلوث جلسات/بصمات/معدلات عبر المواقع |
| 3 | **الملاحظة قبل الفعل (Observe-before-Act)** | لا أتغير بناءً على حدس؛ أتغير بناءً على **إشارة موثقة**: 403، نص challenge، بدء تدهور نافذة 1h/24h |
| 4 | **القرار بالدليل الحي (Evidence-based Ops)** | أي "تعطيل/تفعيل/تصعيد" = probe مأرشف بتاريخ + استجابة + لقطة صريحة |
| 5 | **التماثل في الفشل (Failure Symmetry)** | تشغّل نفس الأنماط على النجاح والفشل معاً؛ النجاح الكاذب (200 ببيانات فارغة) أخطر من الفشل الصريح |
| 6 | **الحد الأدنى للمساحة الهجومية** | لا أدوات/نطاقات/متصفحات أكثر مما يتطلبه السلم الحالي — كل طبقة زائدة سطح كشف |
| 7 | **الامتثال والأخلاق قبل الكود** | robots.txt + ToS + هوية وسيلة الزحف الصريحة + حدود معدل محترمة؛ الفئة F تُحسم قانونياً قبل محاولة تقنية |
| 8 | **التكلفة كحدّ للمعمارية** | كل طبقة في السلم لها "قيمة/جهد"؛ لا أصعّد طبقة تكلفتها تفوق قيمة البيانات التي تعود حالياً |

## 1. تصنيف "العدو": بيئة مزدوجة (BIM — Bot Infra + Site Mechanic)

**خطأ v1.0 الهام:** كان يصنّف **الحماية** فقط. الاحتراف يبدأ بتصنيف **جهاز/آلية الموقع نفسه** أولاً — لأن استراتيجية الزحف الصحيحة تحددها *طبيعة بناء الموقع* قبل *طبيعة حمايته*.

### 1.1 تصنيف آليات الموقع (Site Mechanics) — لماذا يوزّع المحتوى؟

| النوع | الآلية | خصائص الكشف | الاستراتيجية الأنسب |
|---|---|---|---|
| **M1. SSR (Server-Rendered)** | HTML كامل في الرد الأول | DOM كامل لدى أول GET | HTTP + parse خفيف — أرخص وأسرع |
| **M2. SPA (Client-Rendered)** | HTML قشرة + JSON عبر XHR/GraphQL | DOM فارغ حتى JS يُنفَّذ | اكتشاف الـ **API الخلفي** واستهدافه إن أمكن؛ وإلا Browser |
| **M3. API/JSON خلفي** | endpoints موثقة أو مكشوفة | JSON نقي + رؤوس مخصصة | **الأفضل إطلاقاً** — زحف سببه "نموذج بيانات" لا "عرض HTML" |
| **M4. GraphQL** | نقطة واحدة + schema كامل | POST queries هيكلية | استدعاء __typename + schema introspection؛ استخراج بأقل طلب |
| **M5. باجينيشن/تسلسلي** | روابط next/offset/cursor | صفحات قائمة + تفاصيل | سير أعمى عبر cursor على مصدر البيانات (لا على صفحات HTML) |
| **M6. Infinite-Scroll** | تحميل طبقية عبر IntersectionObserver | بدون صفحة "next" | تكرار الـ scroll + التقاط الردود؛ أو اصطياد الـ network XHR مباشرة |
| **M7. Forms/POST-only** | بحث عبر نموذج POST (لا GET قابل للتشاطر) | CSRF token غالباً | فحص آلية البحث أولاً (archive *probeSearchMechanism في مشروعك*) ثم POST مقلد |
| **M8. Auth-walled / Cookie-gated** | جلسة/دفعة عرض قاصمة للمحتوى | 10% محتوى متاح للعموم فقط | **قرار عمل**: API رسمي/شراكة — لا حرب ضد جدار مصادقة |
| **M9. ريديركت/مالتي-دومين** | CDN/عناوين متغيرة أو ميرورز | روابط لا تثبت | قصّ الـ canonical قبل أي dedupe |
| **M10. PDF/صور كمحتوى أصلي** | مرفقات ثنائية | لا HTML | تحويل OCR/مستخرج PDF كمرحلة ثانية مستقلة |

### 1.2 تصنيف أنظمة الحماية (Anti-Bot Taxonomy) — آلية الرد المحتمل

| الفئة | أمثلة | كيف تعمل | الرد المعماري | أولوية الجهد |
|---|---|---|---|---|
| **A. كشف سلبي** | Cloudflare Basic، Akamai | فحص TLS/headers/canvas/webgl | Stealth + تدوير بصمة صحيح + تطبيق سلوك طبيعي | منخفضة — قابلة للحل |
| **B. تحدّي JS نشط** | "Just a moment" (CF)، DataDome | يجب تنفيذ JS في متصفح حقيقي | Headless Browser + انتظار challenge ثم القراءة من DOM بعد الاكتمال | منخفضة–متوسطة |
| **C. CAPTCHA تفاعلي** | Turnstile، hCaptcha، reCAPTCHA | حل تفاعلي أو سلوك مقنع | **الأولوية: تقليل المعدّل لتجنب التفعيل أصلاً** ثم خدمة حل متخصصة كملاذ | متوسطة — مكلف |
| **D. سلوكي/معدلي** | Rate-based ban، honeypot links | مراقبة الزمن/الروابط المخفية | Adaptive rate + تجنّب روابط honeypot + تباعد طبيعي | إلزامية لكل موقع |
| **E. هوية/جلسة** | LinkedIn، Glassdoor | مصادقة حقيقية | **خارج نطاق الزحف الأخلاقي** — شراكة/API | أقصى — قرار أعمال |
| **F. قانوني/ToS** | Terms صريحة تمنع الزحف | ليست تقنية | تقييم المخاطرة القانونية ⟵ قرار مكتوب قبل أي سطر كود | قرار إداري |

### 1.3 مصفوفة القرار المشتركة (M × P)

```
لكل موقع استهداف، بُني جدول قرار:
  Mechanics (M1..M10) ⟶ يحدد "أين تُجنى البيانات" (API أم HTML أم Scroll)
  Protection (A..F)   ⟶ يحدد "كم من السلم نحتاج" (طبقة 0..7)
  
  مثال ذهبي:  موقع M3 + بلا حماية = طبقة 0 (API مباشر) — أسرع و100% قانوني
  مثال مؤلم:  موقع M2 + C (Spa+Captcha) = طبقة 4 → تقييم جدوى قبل البدء
  مثال مصيري: موقع M8 + E        = لا زحف — قرار عمل لا قرار كود
```

> **تطبيق على مشروعك:** Gumtree (M1/A− لحماية خفيفة) وIndeed (M3/API) يفسران درجات A+/A تفصيلياً؛ Bayt (M2+B: SPA+CF) يفسر 403 الموثق؛ OLX/OpenSooq (M2+captcha). **المشكلة ليست قوة المحرك — بل عدم وجود "جدول القرار" المكتوب مسبقاً كمعيار دخول لكل موقع.**

## 2. سلم التصعيد الذكي (Escalation Ladder) + قاعدة التوقف الكمية

### 2.1 السلم (طبقات التصعيد)

| المستوى | الأداة | التكلفة العمرانية | متى نصعد للتالي (إشارة موثقة لا ظنًّا) |
|---|---|---|---|
| L0 | API رسمي/مكشوف | ~0 | لا يوجد API، أو استنفاد quota |
| L1 | RSS/Sitemap/JSON endpoints | منخفضة جداً | لا تغطي حقول المنتج المطلوبة |
| L2 | HTTP + Static Parse | منخفضة | استجابة فارغة من TS (JS لا يصل DOM) أو نتيجة نجاح كاذب |
| L3 | Headless Browser (بدون stealth) | متوسطة | تحدٍ JS صريح ("Just a moment") بعد X محاولة |
| L4 | Browser + Stealth (fingerprint+behavior) | عالية | تحدي تفاعلي / كشف سلوكي متكرر |
| L5 | External (FlareSolverr/CAPTCHA service) | عالية جداً | استمرار الحظر رغم L4 بثقة داخل نافذة 24h |
| L6 | Proxies (سكني/دوران هوية) | الأعلى | استمرار الحظر بنفس هوية IP رغم L5 |
| L7 | **Pause موثّق + جدولة re-probe** | قرار | **تجاوز "قيمة_الموقع ̿ تكلفة_الصيانة"** لهذه الموجة |

### 2.2 قاعدة التوقف الكمية (Stop Rule — العتبة التي كانت تنقص v1.0)

```
يُنفَّذ "قرار L7" تلقائياً عند أيٍّ من:
  1) نفس فئة الحماية بالفشل أثناء نافذة 7d: ≥ 5 محاولات تصعيد فعلية.
  2) معدل الموقع: success_rate < 40% على نافذة متحركة 7d مع ≥ 10 طلبات.
  3) تكلفة تشغيلية: ساعات الإنسان/الطاقة المتصاعدة شهرياً تتفوق على قيمة سجلات الموجة الحالية.
  4) إشارة قانونية: تغيّر ToS/robots يرفع درجة المخاطرة (قرار إنساني إداري — لا تلقائية كاملة).
```
**بعد L7:** لا يتم إعادة التفعيل إلا بـ (أ) probe حي جديد موثق 200 + (ب) تحديث config + (ج) إعادة فتح ADR. أي إعادة تفعيل بدون ADR مكتوب = انحدار حوكمة.

## 3. المعمارية الطبقية الإلزامية (12-Layer) + العقود بين الطبقات

```
┌─────────────────────────────────────────────────────────────┐
│ L12  الحوكمة والتوثيق الحي (Docs-as-Code + ADR + Ownership)  │
├─────────────────────────────────────────────────────────────┤
│ L11  المراقبة والقياس (metrics / logs / alerts / dashboards) │
├─────────────────────────────────────────────────────────────┤
│ L10  مصنع التقارير (HTML/Deck/CSV/XLSX — Export Views فقط)   │
├─────────────────────────────────────────────────────────────┤
│ L9   طبقة البيانات الموحدة (documents + جداول متخصصة)        │
├─────────────────────────────────────────────────────────────┤
│ L8   محركات الذكاء (تصنيف/تسجيل/لدوب/تعلم عبر المواقع)        │
├─────────────────────────────────────────────────────────────┤
│ L7   التنسيق والجدولة (Orchestrator / Queue / Scheduler)     │
├─────────────────────────────────────────────────────────────┤
│ L6   الاستخراج القانوني لكل منطقة (Canonical per-locale)     │
├─────────────────────────────────────────────────────────────┤
│ L5   مكافحة الاكتشاف (Fingerprint + Behavior + Stealth)      │
├─────────────────────────────────────────────────────────────┤
│ L4   تحديد المعدّل وإدارة الموارد (rate/semaphore/bucket)    │
├─────────────────────────────────────────────────────────────┤
│ L3   محرك الاستراتيجية المتدرج (L0→L7 + Stop Rule)           │
├─────────────────────────────────────────────────────────────┤
│ L2   النقل (Transport: HTTP/RSS/Browser/Proxy/Flare)         │
├─────────────────────────────────────────────────────────────┤
│ L1   المدخلات والتهيئة (Site Registry / Config / Secrets)    │
└─────────────────────────────────────────────────────────────┘
```

### العقود الملزمة (Interface Contracts) — أهم قسم في هذا الفصل

| # | العقد (Interface) | الضمان | التنفيذ في مشروعك |
|---|---|---|---|
| C1 | `Registry.getSiteConfig(host)` | config صحيح/مكتمل أو يقترف Fail-fast | `core/site-adapter.mjs` ✅ |
| C2 | `Transport.fetch(url, ctx)` | معرف نوع الاستراتيجية والعودة بشكل قياسي | `core/strategy-engine.mjs` ✅ |
| C3 | `Extractor.parse(html|json|dom, site)` | سجل Canonial قياسي خرج من كل شكل | `core/canonical-extractor.mjs` ✅ |
| C4 | `Data.write(doc)` | يصل `documents` حصراً — لا توجد مسارات جانبية للكتابة | **فجوة: JSON بكثرة** |
| C5 | `Intel.score(doc)` | يعيد confidence/dup قبل الكتابة | `core/insight-engine.mjs` ⚠️ غير مفعّل بالسلسلة |
| C6 | `Metrics.record(run)` | كل تشغيل يرصد comfort حي (نافذة 1h/24h/7d) | **فجوة R7** |
| C7 | `Governance.assert(permission)` | أي قرار تصعيد/تعطيل يمر بحارس امتثال+ADR | **فجوة D2/D3/D4** |

> **قاعدة صارمة:** إذا استطاع **محرك طبقة علوية** استيراد **تفاصيل طبقة أدنى** مباشرة، فالعقد منكسر. مثال يُمنع: L8 تشير إلى `anti-detect` داخلها. التعديل الوحيد المسموح هو عبر واجهة L3/L4 المعلنة.

## 4. الأنماط الهندسية الإلزامية (Resilience Patterns)

| النمط | الغرض | عتبة/تنفيذ نموذجي | أين ينطبق |
|---|---|---|---|
| **Circuit Breaker** | منع الانهيار المتتالي لكل موقع | CLOSED → (5 فشل متتالي) → OPEN → (cooldown ثم probe) → HALF-OPEN | لكل موقع (site-level) |
| **Bulkhead (Isolation)** | عزل جلسات/معدلات/بصمات كل موقع | pools منفصلة (browsers/cookies/proxies) لكل host | عبر المواقع |
| **Retry + Exponential Backoff + Jitter** | امتصاص الرجفان المؤقت | 3 محاولات، مضاعفة 2x، jitter 0.2 | لكل طلب فاشل عابر |
| **Idempotency** | إعادة تنفيذ بلا ازدواجية | مفتاح `(source,url_hash)` قبل الكتابة | الكتابة للـ DB |
| **Timeout لكل مرحلة** | منع تعليق المهمة المنسية | navigation 30s / adPage 20s / http 8s محددة سلفاً | كل fetch |
| **Dead-letter / Queue العزلة** | عزل مهمة فاشلة عن المعالجة | طابور per-host + DLQ للفشل الهابط بعد maxRetries | L3/L7 |
| **Chaos via Probe** | اختبار الفشل الحقيقي بانتظام | probe مجدول أسبوعي لكل موقع OPEN | حوكمة التشغيل |
| **Kill Switch عام** | إيقاف شامل فوري بلا فقدان طابور | flag تشغيل + انتهاء الجولة الحالية بأمان | أتمتة الإنتاج |

## 5. طبقة البيانات الموحدة (Single Source of Truth) — محل D1

### 5.1 النموذج المطلوب (قابل للتطبيق على SQLite وPostgres)

```
الاستخراج (كل المواقع/الأنواع)
      │
      ▼
  documents(id, source, url, url_hash UNIQUE, type,
            kind, raw_json, canonical_json, contacts_json,
            status, confidence, fetched_at, updated_at)
      │                     │
      ▼                     ▼
  جداول متخصصة (tenders,   contact-miner:  report-factory:
  contractors, projects)    يقرؤ نفس الجدول     يقرأ نفس الجدول
                            فيضيف أعمدة/نقاط  فيولّد Export Views
```

### 5.2 قواعد صارمة
1. **JSON/CSV/XLSX/HTML = صيغ تصدير فقط، لا مخزن** (Export Views).
2. `url_hash` هو المعرّف الوحيد المستقر — أي dedupe قبل الكتابة + upsert بعده (`ON CONFLICT(url_hash) DO UPDATE`).
3. `raw_json` يُحفظ **دائماً** (أرشيف جنائي) و`canonical_json` يُحفظ **دائماً** (بيانات التشغيل) — لا أحدهما فقط.
4. أي عملية تصدير/تعلم/ذكاء تقرأ من الجدول لا من الملفات — يضمن زوال ازدواجية D1 نهائياً.
5. فهرس مفهرس على `(source, fetched_at)` + أي استعلام بالحجم يعمل بـ SQLite/WAL في المرحلة الحالية.

### 5.3 خطوات الترحيل (Migration Path) لـ CSI-Ultimate
```
المرحلة 1: إنشاء جدول documents + mapper من canonical-extractor الجاهز
المرحلة 2: جعل general-crawl/contact-miner يكتبان إلى الجدول بدل الملفات
المرحلة 3: توجيه report-factory/export لقراءة الجدول (الملفات = cache مؤقت فقط)
المرحلة 4: جدولة تدقيق تكامل أسبوعي (count(JSON مقروء) == count(DB records))
```

## 6. هرم اختبار السكرابر + الملفات الذهبية

### 6.1 الهرم (مخصص لبيئة تتغير — ليست الهرم التقليدي)

```
         ▲  Live Probes (مجدد عبر scheduler لا داخل CI العادي)
        ╱ ╲    يتحدث "حالة الموقع" تلقائياً ويثبت/ينفي دليل إعادة التفعيل
       ╱───╲
      ╱ Contract╲  Fixture Tests: HTML/JSON مجمد كغولدن (golden files)
     ╱   Tests   ╲  لكل موقع + لكل آلية (M1..M10) — يثبت أننا لم نكسر فهمنا
    ╱──────────────╲
   ╱    Unit Tests    ╲  استخراج/تطبيع/dedupe/كشف ban بمعزل عن الشبكة
  ╱────────────────────╲
 ╱        Static / Линт     ╲  node --check + رفض import عشوائي بين الطبقات
╱────────────────────────────╲
```

### 6.2 قراءة نتيجة الفشل (إزالة الإنذارات الكاذبة)
| نوع الاختبار فشل | المعنى | الإجراء |
|---|---|---|
| Unit/Fixture فشل | **كسرناه نحن** | تصحيح كودنا + لا تمسح الـ fixture قبل التحديث المتعمد المدبر بالتاريخ |
| Live Probe فشل | **الموقع تغيّر** | فتح ADR + تحديث config/site + جدولة re-probe |
| الاثنان معاً فشلا | كسرنا وموقع تغير معاً | ترتيب: أصلح الـ parser أولاً ثم أعد الـ probe بعد استقرار كودنا |

### 6.3 ممارسات إلزامية
- كل **site-config جديد** بدون fixture golden + اختبار contract = مرفوض PR.
- `npm run lint` (node --check) تُشغَّل على core/web/config في CI (موجود فعلاً — يُنشر كشرط اجتياز).
- CI ثنائي Node 20/22 (موجود) + إضافة مصفوفة 24 لإثبات الاستقرار.
- Golden update يتم عبر قيادة صريحة `--update-fixtures` مع ربطها بتعديل المشروع الحقيقي، لا تلقائياً.

## 7. المراقبة والقياس: حزمة مقاييس إلزامية + لوحة قرار (محل R7)

### 7.1 حزمة المقاييس (تُصدر لكل موقع بشكل دوري وتُجمع في لوحة واحدة)

| المقياس | التعريف | القرار المتصل |
|---|---|---|
| `success_rate_1h/24h/7d` | نافذة متحركة للنجاح | كشف التدهور قبل الانهيار |
| `escalation_level_avg` | متوسط طبقة السلم خلال النافذة | مؤشر مبكر لزيادة حماية الموقع |
| `ban_signals_count` | عدد 403/429/CF-challenge/nonsense | تهييج Circuit Breaker |
| `records_per_run` + `delta_vs_baseline` | ناتج فعلي مقابل خط الأساس | كشف **نجاح كاذب** (200 ببيانات فارغة) |
| `latency_p50/p95` | زمن الاستجابة | كشف throttling خفي قبل ban |
| `last_live_probe_ts/result` | آخر تحقق حي وتوقيته | شفافية القرار (تعطيل/تفعيل) |
| `distinct_ips_used` + `proxy_fail_rate` | استهلاك/كسر البروكسيات | قرار تجديد/دوران |
| `cost_per_record` | تكلفة تشغيلية/طاقة لكل سجل | دست العتبة الكمية لـ L7 |

### 7.2 شروط تنبيه إلزامية (Alert Rules)
| الشرط | الأولوية | الإجراء |
|---|---|---|
| `success_rate_24h < 60%` لأي موقع نشط | P1 | إنذار + تباطؤ تلقائي 2x |
| `ban_signals_count > 5` خلال 10 د | P1 | Circuit Open تلقائي |
| `delta_vs_baseline < -50%` رغم success>90% | P0 | **نجاح كاذب** — أفحص parser فوراً |
| `proxy_fail_rate > 30%` | P2 | دوران تلقائي للبركة |

> R7 في تقريرك = تفعيل هذا الفصل بالضبط على `/api/v1/dashboard` — ويمكن أن يبدأ من مقاييس حيوية بسيطة تتصاعد أسبوعياً.

## 8. الحوكمة: ملكية + ADR + سياسة الإهلاك (محل D2/D3/D4)

### 8.1 قاعدة الملكية الإلزامية
- أي ملف كود بـ `scripts/` أو كلاس جديد يفتقد ترويسة: `@owner <اسم> @purpose <سطر> @last-reviewed <ISO>` يُنقل تلقائياً إلى `scripts/archive/` بعد 30 يوم بلا استخدام **سكربت CI** (وليس قراراً بشرياً كل مرة).
- أي `app/` قديم أو `engine/` shim يتم:
  1. وسمه `DEPRECATED` في الترويسة.
  2. **إعادة توجيه HTTP** للمنفذ الرسمي بدل تشغيله بالتوازي (التوازي = أخطاء صامتة).
  3. حذفه بعد بلوغ صفر استخدام في السجلات أسبوعياً ×4 متتالية.

### 8.2 نمط قرار معماري (ADR — Architecture Decision Record)
Aي ADR ملف قصير (≤ صفحة) يُكتب عند كل قرار غير قابل للتراجع منه:
- العنوان + الوضع (النطاق/المتأثرون)
- السياق سبب القرار بما فيه الملفات المتأثرة
- الخيارات المرفوضة وسر رفضها (سطر لكل منها)
- القرار المختار (فكرة واحدة) — يُكتب كـ "قررنا أن <X> لأجل <Y>"
- النتائج: عواقب موجبة وسالبة متوقعة
- المسار: تاريخ القرار + `last-live-probe` المعتمد عليه إن كان تعطيل/تفعيل موقع

> **تطبيق فوري:** قرار "تعطيل Bayt 2026-09-11" يجب أن يبقى كـ `docs/decisions/ADR-2026-09-11-bayt-suspend.md` بدل الوصف في README المبعثر.

### 8.3 التوثيق كارتفاع تنفيذي (Docs-as-Code)
- لا حقيقة تعمل إلا هي مكتوبة: لكل طبقة ق آلياتها وتعريف ناجح معلن في `docs/`.
- أي فرق بين الوثيقة والكود = نقص يوضع كبند جودة للـ PR التالي (اسحب من D4).

## 9. نموذج النضج L1–L5 مع معايير خروج (Exit Criteria) كمية

| المستوى | الوصف | معايير الدخول | معايير الخروج (للارتقاء) |
|---|---|---|---|
| **L1** بدائي | سكربتات منفصلة لكل موقع | لا استراتيجية/لا عزل | محرك استراتيجية موحد لموقعين على الأقل |
| **L2** منظّم | وحدة استراتيجية + rate + canonical | 2+ مواقع تعمل بنفس الدليل | كل المواقع يقرؤ Upon same Registry + 100% extraction يمر canonical |
| **L3** مرن | Circuit Breaker لكل موقع + probes + CI | مواقع معاملة كدائرات مستقلة | — ← **CSI-Ultimate هنا (B+→A−)** |
| **L4** ذاتي التكيف | DB موحد + لوحة مقاييس حية + ذكاء مفعّل | probing تلقائي | كل كتابات البيانات عبر C4؛ R7 حي؛ محركات L8 على الخط الرئيسي |
| **L5** منتج مستقل | Orchestration خارجي (n8n) + lead scoring + SLA | L4 مستقر 2+ أسبوع | عميل يستهلك API/تصديرات من ج قيادة موثقة — SLA مكتوب |

**قاعدة تسوية:** لا يمر مشروع من L3 إلى L4 بدون تحقق **كل** معايير خروج L4 في تقرير قبول مكتوب. الـ Exit Criteria ليست أمنيات — أرقام قابلة للفحص.

## 10. دورة التطوير الديناميكي (SLAM Loop) — منهجية "اصنع–اثبت–تكيف–تعلّم"

هذا هو قلب "التطوير المنهجي الديناميكي" الذي طلبت إدماجه. كل ميزة/موقع/إصلاح يمرّ بهذه الحلقة — باسم صريح وقابل للعرض (SPRINT لا يخرج عن مدار الحلقة):

```
 S  Scan   — امسح الهدف: Mechanics (M) + Protection (P) + قيمة المنتج + المخاطرة
 L  Ladder — اختر نقطة البداية في السلم (ابدأ بالأرخص لTI = L0/L1 ما أمكن)
 A  Apply  — نفّذ بسور ملكية + fixtures + اختبار contract + عقد الكذب الكتابية
 M  Measure— راقب المقاييس الإلزامية في نافذة 7 أيام (لا قرار قبل الأرقام)
          ↑  ... وعد (Loop):
       تكيّف: إن انحرف مؤشر → عُد لقرار التصعيد/التوقف وفق العتبات الكمية
       تعلّم: سجّل النتيجة في ADR + موقع/nT profile + تعلّم عبر المواقع
```

### قواعد الحلقة
1. **لا خطوة A بدون S** — أي محاولة زحف بدون تحديد M/P هي تخمين يُرفض في المراجعة.
2. **لا خطوة M بدون A** — أي كود بلا مقاييس معروفة لا يغادر ورشة العمل.
3. **الحلقة تُغلق بوثيقة، لا بالذاكرة** — خروج الموقع من الحلقة = ADR.
4. **الدورات فريدة من حيث التكرار والمدّة**: ميزة CRUD = أيام؛ موقع محظور = أسابيع مع فحص أسبوعي؛ تكامل n8n = موجات مشروع.

## الخلاصة النهائية (Executive Bottom-Line)

النظام "غير قابل للكسر" ليس ما لا يفشل — بل ما:
1. **يكشف الفشل خلال ثوانٍ** (L11 + Alert Rules).
2. **يعزل الفشل ولا يسحبه إلى الموقع التالي** (Circuit + Bulkhead).
3. **يوثّق سبب الفشل بدليل حي** (Live Probe + ADR).
4. **يحسم بصمت: يصعّد أم يتوقف بـ"رقم" لا بشعور** (Stop Rule 2.2).
5. **يتعلم من الفشل عبر حلقة مغلقة** (SLAM) ويراكم في **مصدر حقيقة واحد** (L9).

**كل ما سبق مطابق لمشروعك في الفجوات الحقيقية:** أولويتك المعلنة في تقرير التحليل (R1) ليست اختياراً — هي نتيجة بنيوية: لا يمكن أن تنضج L10/L8/L11 فوق مصدر قيادة مزدوج. ابدأ من W1 أعلاه، وأغلق كل ما سبق بـ ADR موثق، وسيصبح CSI-Ultimate نظاماً يُقايَس بـ L4-L5 بدلاً من L3 مع عتبة جودة A− وأسعار ثابتة.
