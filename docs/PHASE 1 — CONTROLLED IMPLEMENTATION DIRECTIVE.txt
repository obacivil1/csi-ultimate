PHASE 1 — CONTROLLED IMPLEMENTATION DIRECTIVE

Project: SPECIALIZED VULNERABILITY DETECTION ENGINE
Specializations: Race Conditions / TOCTOU + Advanced Authorization
Phase: PHASE 1 — FOUNDATION / CONTRACTS
Status: AUTHORITATIVE
Mode: CONTROLLED IMPLEMENTATION
Prerequisite: PHASE 0 — ARCHITECTURE DISCOVERY — APPROVED
Implementation Policy: ADDITIVE, REVERSIBLE, MINIMAL-DIFF
Primary Rule: Build the security-engine foundation. Do not implement vulnerability detectors in this phase.

1. MANDATE

Implement Phase 1 only.

The purpose of this phase is to establish the minimum stable foundation required for later development of:

Advanced Authorization Engine.
Race / TOCTOU Engine.
Workflow / State Intelligence.
Evidence and finding validation.
Cross-engine correlation.

Phase 1 is not a detector implementation phase.

The implementation must be additive and isolated from existing application behavior.

The resulting architecture must allow future security detectors to consume normalized security objects without modifying the existing crawler, recon, scope, reporting, authentication, or detector implementations.

2. PHASE 1 OBJECTIVE

Create a new isolated security-engine foundation containing:

normalized security-domain models;
Identity and Session contracts;
Target / Endpoint / Request / Response contracts;
Resource / Workflow / State contracts;
Observation / Evidence / Finding contracts;
correlation-ID support;
unified security-engine scope-gate interface;
detector registry contract;
execution contract;
differential-analysis contract;
minimal storage-independent interfaces;
tests proving the contracts and safety boundaries work.

The foundation must be usable by both future engines:

                    SECURITY ENGINE
                          │
          ┌───────────────┴────────────────┐
          │                                │
 Authorization Engine                Race Engine
          │                                │
          └───────────────┬────────────────┘
                          │
                Shared Security Model
                          │
       Target / Endpoint / Request / Response
       Identity / Session / Resource / State
       Observation / Evidence / Finding
                          │
                Existing Infrastructure

8. LANGUAGE POLICY

The repository currently uses:

Node.js ESM / .mjs
Python / .py

Do not introduce TypeScript.

For Phase 1:

Node implementation should use .mjs.
Python implementation should use .py only where required.
Data contracts must be language-agnostic.
JSON-compatible representations are preferred for cross-language exchange.

Do not create two conflicting definitions of the same security concept.

Where both languages require a model, the semantic contract must be identical even if implementation syntax differs.

9. CORE SECURITY DOMAIN MODEL

Implement contracts/models for the following concepts.

9.1 Target

Minimum conceptual fields:

target_id
base_url
scope_reference
environment
metadata

The model must not silently imply authorization.

Authorization status must be represented explicitly.

9.2 Endpoint

Minimum conceptual fields:

endpoint_id
target_id
scheme
host
port
path
method
parameters
authentication_context
resource_reference
metadata

Do not assume every endpoint is authenticated.

Do not assume every endpoint is state-changing.

9.3 Request

Minimum conceptual fields:

request_id
correlation_id
endpoint_id
method
url
headers_metadata
parameters_metadata
body_hash
identity_reference
timestamp

Secrets must not be stored in cleartext by default.

Cookies, authorization headers, passwords, tokens, and credentials must be represented through safe references or redacted metadata.

9.4 Response

Minimum conceptual fields:

response_id
request_id
correlation_id
status
headers_metadata
body_hash
content_type
body_length
timing
state_indicators

Do not store full response bodies by default.

The architecture must allow secure evidence references later.

10. IDENTITY MODEL

Create a first-class Identity contract.

Minimum conceptual fields:

identity_id
label
role
tenant_id
authorization_context
session_reference
metadata

Examples:

User-A
User-B
Admin
Tenant-A-User
Tenant-B-User

These are conceptual identities only.

Phase 1 must NOT implement target login automation.

11. SESSION MODEL

Create a Session contract capable of representing future authenticated target sessions.

Minimum conceptual fields:

session_id
identity_id
target_id
authentication_method
created_at
expires_at
status
credential_reference
cookie_jar_reference
header_reference
metadata

Security requirement:

Never expose or persist raw passwords, bearer tokens, session cookies, or equivalent secrets in normal logs.

The contract must support session isolation.

A session belonging to Identity A must never be implicitly reused as Identity B.

12. RESOURCE / OBJECT MODEL

Create a Resource/Object abstraction.

Minimum conceptual fields:

metadata

The model must support later analysis of:

ownership
tenant isolation
role boundaries
object identifiers
state transitions

Do not implement BOLA detection yet.

14. OBSERVATION MODEL

Minimum conceptual fields:

15. EVIDENCE MODEL

Create a first-class Evidence abstraction.

Evidence must be traceable to observations.

Minimum conceptual fields:

evidence_id
observation_id
type
description
reference
hash
redaction_status
truncated
metadata

Important:

If evidence is truncated, the model must explicitly record:

truncated = true

Never silently truncate security evidence.

16. FINDING MODEL

Create a generic security Finding contract suitable for both future engines.

Minimum required fields:

finding_id
finding_type

The finding model must explicitly separate:

Confidence
Impact
Severity

Do not collapse them into one score.

A finding must also distinguish:

candidate
validated
rejected

or an equivalent lifecycle.

17. CORRELATION ID

Introduce correlation IDs at the security-engine layer.

Every security execution, request observation, evidence item, and finding must be traceable to a correlation context.

Minimum requirements:

correlation_id
execution_id
request_id
observation_id

IDs must be generated deterministically enough for traceability but unique enough to prevent collisions.

Do not alter the existing global logger architecture in Phase 1.

18. SECURITY SCOPE GATE

Create a security-engine scope interface.

It must provide a single conceptual entry point such as:

assertAuthorizedTarget(...)

The adapter must verify the applicable existing scope controls.

Requirements:

deny ambiguous scope;
deny missing authorization context;
deny expired authorization where the existing scope model supports validity;
deny excluded hosts/paths;
preserve existing SSRF protections;
preserve existing scope semantics.

Do not rewrite the existing scope validators.

The new gate is an adapter/orchestration boundary.

19. DETECTOR REGISTRY

Create a detector registry contract.

The registry must support:

register
unregister
enable
disable
list
resolve
execute

A detector definition should identify at minimum:

detector_id
name
version
specialization
required_capabilities
scope_requirements
status

Phase 1 requirement:

No vulnerability detector may be enabled by default.

The registry must be capable of operating with zero detectors.

Do not implement Race/BOLA/BFLA detectors in this phase.

20. EXECUTION CONTRACT

Create a generic execution contract that future detectors can use.

The execution layer must understand:

target
scope
identity
endpoint
request
budget
timeout
correlation

It must not yet implement synchronized race dispatch.

It must provide a future-compatible abstraction for:

sequential execution
bounded parallel execution
synchronized execution

but only the minimal foundation required for Phase 1 should be implemented.

Do not build the Race Engine here.

21. DIFFERENTIAL ANALYSIS CONTRACT

Create a minimal comparison abstraction capable of comparing two or more observations.

It should support comparison categories such as:

status
headers
response structure
selected fields
body hash
timing
state indicators
resource state

The result must distinguish:

same
different
inconclusive

Do not implement vulnerability decisions.

The differential engine answers:

"What changed?"

It does not answer:

"Is this a vulnerability?"

22. STORAGE POLICY

Phase 1 must be storage-independent.

Do not create a new permanent database unless strictly required.

Prefer interfaces such as:

EndpointStore
IdentityStore
SessionStore
ObservationStore
EvidenceStore
FindingStore

A minimal in-memory implementation is acceptable for Phase 1 tests.

The architecture must allow a persistent backend later without changing detector contracts.

Do not modify data/csi.db.

23. ADAPTER POLICY

Where existing infrastructure is consumed, use adapters.

Examples:

Existing HTTP client
        ↓
HTTP adapter
        ↓
Security Request/Response model
Existing scope system
        ↓
Scope adapter
        ↓
Security Scope Gate

Do not duplicate:

HTTP clients;
SSRF checks;
rate limiters;
audit chains;
browser security controls.

Reuse existing infrastructure through controlled interfaces.

24. SECURITY / SECRET HANDLING

The new models and logs must not leak:

passwords;
bearer tokens;
session cookies;
API keys;
authorization headers;
credentials.

Evidence must support hashes/references rather than requiring plaintext secrets.

Redaction must occur before persistence or logging.

If existing redaction utilities are insufficient for the new model, add the smallest isolated adapter necessary.

Do not weaken existing privacy controls.
